# CB9-600 确定性单元、集成、契约与 traceability 测试

**AC-036 PASS**（NFR-006）

## oracle

「对**模式隔离、幂等、位置隐私、Status 新鲜度**各注入至少一个反例；
错误实现必须导致测试失败。」

## 为什么这条验收本身要存在

一套全绿的测试可以什么都不证明。三种情况下套件都是绿的而产品是坏的，
这一程里全都撞见过：

- 测的是模块自己的性质，而不是产品的性质
- 断言松到任何实现都满足（DST 那次：「不是 02:xx」被一个错误答案满足了）
- 守卫压根没接到真实链路上（`joinTimezoneSignal` 那次，19 条适配器测试全绿）

唯一能反驳「这套测试其实没在测东西」的证据，是**把实现改坏，看测试红不红**。

## 交付的是一个脚本，不是一次跑动

`app/scripts/mutation-acceptance.js`，提交进仓库。
任何人任何时候 `node scripts/mutation-acceptance.js` 都能重跑出同一份结论。

这和之前逐节点手跑的红绿不同：手跑的那种只存在于某一次会话的记录里，
而一份复现不了的证据在几周后等于没有。

## 结果

**基线 0 红，13/13 转红**（见 `mutation-report.json`）：

| 维度 | 刀数 |
|---|---|
| 模式隔离 | 3 |
| 幂等 | 3 |
| 位置隐私 | 3 |
| Status 新鲜度 | 4 |

每一刀都是**一个真实的错误决定**——判反了、少查一个条件、把守卫摘掉——
不是语法错误，也不是删掉整个函数。那两种谁都拦得住，证明不了判别力。
每一刀还必须写清「这样改了会怎样」：一个说不出后果的变异，红了也不知道红得对不对。

## 三条把脚本本身钉住的规矩

**锚点失效算失败，不算跳过。** 代码改了、锚点没跟上，脚本会一边什么都不注入
一边报「全红」——那比没有变异测试更糟。第一次跑就抓到一条锚点失效
（`safeObservation(raw)` 实际是 `safeObservation(raw = {})`）。

**恢复源码那一步在 `finally` 里。** 顺序执行的话，中间抛异常就把一份改坏的代码
留在工作树里，而它看起来是正常的。

**普通 `npm test` 里就能红。** `test/cb9-600-mutation-acceptance.test.js` 检查
四个维度一个不缺、每一刀的锚点在当前源码里唯一命中、每一刀都说得出后果——
不用等谁想起来跑那个脚本。

## traceability

`traceability.json`：DAG 37 个节点的证据落位对账。
30 个有证据目录，缺的 7 个全部是 `environment_bound`（`CB9-010` 和 S6 的五个），
它们的 NOT_RUN 记录随对应节点提交。

## 回滚

一个新脚本 + 一个新测试文件，不改产品代码。回滚 = 删除这两个文件。

## 两个真实缺陷

**F1（高）· 位置上报服务默认绑 `0.0.0.0`。**
`src/core/config.js` 的 `locationHost` 默认所有网卡，而 `whereabouts-mcp` 真的
拿它去 `server.listen(port, host)`。它是**位置上报入口**——谁打得到，
谁就能往这台机器里写主人的行踪，而它自己只有一个可选 token。

AC-032 的原话就点了这条（「监听扫描无 0.0.0.0」），而它一直是绿的：
**从来没有一条测试去扫过监听面**。改成 `127.0.0.1`，要对外走隧道。

**F2（高）· 经纬度和 IP 只在不鉴权出口被挡住。**
CB9-520 把键黑名单收窄到不鉴权出口，是为了不让后台对话页被清空（那份清单里有
`text`/`content`/`body`）。收窄收对了，但收过头了——`{latitude: 31.23}` 在
`/me` 和 `/admin` 上畅通无阻。

补了一份**任何出口都不许出现**的字段集（坐标、IP、凭据），和 Timeline 那份完整
黑名单分开：坐标和 IP 在哪儿都不该有，因为 FR-021 说这个产品根本不采集它们——
主人自己那一页也不该有他自己的经纬度，我们压根没存过。

## 提示注入：防线不是过滤句子

过滤句子是打地鼠：换个说法、换种语言、拆成两条消息，全绕过去。
真正的防线是**用户说的话根本不参与授权判断**。

所以六条注入样本验的不是「我们认出了这是注入」，是「认不认得出都无所谓」。
另加一条结构断言：`UserContext.may()` 的函数体里没有一处碰得到
`text`/`message`/`content`/`prompt`/`body`——文本影响不了授权，
不是因为我们过滤了它，是因为那条路上根本没有它。

顺带发现 `UserContext` 是冻结的：注入文本连挂都挂不上去，那本身就是一层防线。

## 秘密扫描：真凭据 vs 拒绝用的样本

这个仓的隐私测试里有几个 GitHub token 形状的占位符，用来证明扫描器会拒绝它们。
按形状粗暴报警会把它们全报出来，而**一份天天误报的扫描报告，等真出事那天
没人会看**。也不能给测试文件开后门——真泄漏最可能就发生在测试里。

判据用**序列性**：真凭据是随机的，占位符是照着字母表敲的。
相邻字符在 ASCII 上连号的比例超过一半就是占位符。
（熵不行：一遍字母表加 0-9 每个字符都不重复，按熵算反而最高。）
私钥则要求 BEGIN 头后面连着 base64 主体——光一行头是样本，不是能用的东西。

判据本身也有测试钉着：判反了整条扫描就废了，不是漏报就是天天误报。

## 一个自己撞上的

这份说明的注释里一开始把那个占位符**原样抄了进来**，仓库自己的 AC-038 扫描当场
报红。它报得对：扫描器分不出注释和代码，也不该分——一个「只是举个例子」的真
token，泄漏起来一样彻底。

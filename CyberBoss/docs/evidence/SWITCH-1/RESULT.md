# SWITCH-1 一键上下线

主人的原话：「可以在网页端直接决定整个系统能否正常运行」。

## 「能否正常运行」最容易被做成假货的读法

**只是不回话。** 消息照样入库、事实照样落盘、队列照样堆，只是嘴闭上了。
那不叫停机，那叫静音——而主人按下这个按钮时想的往往正是「先别再往里存东西了」。

所以闸装在 `handleIncomingMessage` 上，**在准入之前、在建 job 之前、
在任何模型调用之前**。那是真实链路上每条消息的必经之路。

## 三个不那么显然的决定

**一、「没有状态文件」和「状态文件坏了」不是一回事。**

- 文件不存在 = 从来没人碰过这个开关 → **跑**。新装好的系统不该因为主人还没
  点过按钮就是停的。
- 文件在但读不出来 = 我们曾经有过一个状态，现在丢了 → **停**。

两害相权：停错了主人点一下就好；跑错了——在他可能已经说过「停」的情况下继续
收消息、继续存数据——处理掉的消息和存下的数据收不回来。

**二、主人自己必须能把它打开。**

关掉之后如果连主人的「上线」也被挡住，唯一的复活方式就是 SSH 上服务器——
那这个按钮对一个不会 SSH 的人来说是个**单向陷阱**。所以闸上有一条明确例外，
而且只认服务端配置里的 sender id，不认消息文本里的自称。

**三、停机期间同一个人只回一次。**

每条都回的话，一个正在连发消息的人会收到一串一模一样的回复——那比不回更烦，
而且是我们主动发的，等于停机之后系统反而更吵。重新上线会清空台账，
否则下一轮停机时老用户什么都收不到。

停机那句话不承诺恢复时间：我们并不知道主人什么时候会打开它，
而一个没有兑现的「稍后」比不说更伤。

## 一个被测试顶出来的设计错误

第一版把「没配开关文件路径」和「状态文件坏了」归成同一类，一起往「停」落。

那是错的，而且错得很危险：哪天有人重命名了这个 config 键，
**整个产品会直接全黑**，而用户看到的是一句「主人手动关掉了」——一句彻头彻尾的假话。

抓到它的是那几条走真实入站路径的既有测试：它们的 harness 没有配这个路径，
于是每一条消息都被挡下了。纯函数测试全绿，因为它们都显式传了路径。

现在「没接上」落在**跑**，但面板上明说按钮按不动。

## 变异测试顶出来的两个真缺口

13 刀全红，基线 0（见 `mutation-report.json`）。两刀第一轮活着：

- **「主人的上线口令也被挡住」存活** —— 把那整个分支关掉，全套测试照样全绿。
  也就是说，我写了注释警告「单向陷阱」，却没有一条测试真的走过那条路。
- **「重新上线不清通知台账」存活** —— 我单独测了 `ledger.reset()`，
  没测**谁在调它**。

两条都补了走真实 `handleIncomingMessage` 的测试。

## 面板

开关放在概览**最上面**——埋在设置里的开关等于没有，真出事的时候他找不到。
按钮 44px 可点下限。显示三种状态而不是两种：开着、停着、以及**开关本身不健康**。

停机是影响所有人的操作，点之前问一句；开机不问——那是在修东西，
每次都拦一下只会让人烦。

## 接口

`GET/POST /admin/api/system-switch`，和后台对话/语气同一条鉴权。
只认真正的布尔值：收 `"false"` 这个字符串会被 JS 当成真，
那意味着主人点「停」而系统听成了「开」——是这个接口最不能犯的错。

网页端和微信口令走同一个 `setSystemSwitch`，有测试钉住 `writeSystemSwitch`
在 app.js 里只出现一次。

无迁移、无数据变更。回滚 = `git revert`，系统回到「永远开着」。

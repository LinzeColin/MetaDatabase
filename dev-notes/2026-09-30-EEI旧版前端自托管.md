## 证据栏：真实原因与修法

验收旅程「点开证据栏看来源」在 `click_text: 证据栏` 失败，原因有三层，都修了：

1. **宽屏（≥1280px，桌面/暗色视口 1440）根本没有「证据栏」可点**：右栏常驻，唯一带「证据栏」字样的浮动开关被 CSS 隐藏（`display:none`）。手机视口有，所以手机能点到。修法：右栏标题旁加可见按钮（图标 + 文字「证据栏」、`title` 提示、`aria-controls`，是原生 `<button>`，Tab 可达）；点它把证据面板滚到眼前、给键盘焦点并高亮 2.4 秒。窄屏仍是右下浮动开关，同一个处理函数，并补了 `title`/`aria-controls`。
2. **证据面板常常是空的**（两个异步取数互相覆盖）：云模式下 `hydrateProductionGraph` 之后还会跑本地工作台的 `hydrateProductionData`，它在云取数之后返回，把证据面板覆盖成 `local_fallback / object_id_missing`（「0 条摘录」）。修法：云模式下 `hydrateProductionData` 不再走本地流程，改为转给 `hydrateCloudData`。
3. **页面每次打开都留两条同源 404**：`/v1/catalogs`（已随 2 消失）与 `/v1/scoring/profiles`（云发布面没有这条路由）。验收执行器把任何同源 ≥400 都算失败，所以整条旅程在所有视口都过不了。修法：云模式不请求 `/v1/scoring/profiles`。
4. 顺带：深空主题下右栏「所选节点」卡与证据面板用的是浅色主题底色，文字却继承浅色，证据标题与「N 条摘录」几乎看不见——补了深空配色。
5. 顺带：首屏这一行云模式下叫「数据截至」，而验收旅程 `EEI.yaml` 的新鲜度检查按 `数据版本 · YYYY-MM-DD` 取日期，改为云模式也叫「数据版本」。**这是文案改动，主人若偏好「数据截至」，应改旅程里的 pattern 而不是改回来。**

另把右栏的「关系路径列表 + 证据面板」挪到「保存视图」面板之前（证据是右栏的名字，原来埋在 2600px 高的右栏中段）。

## 给主线的部署步骤（逐条）

合并后，在 VPS-3 上（root）。顺序很重要：**先装新部署器与 env，再触发部署**。若只等定时器，它会用旧 env 构建新 Dockerfile——失败并保留旧容器（安全，但会记一次退避），不会影响线上。

```bash
# 1. 取最新部署件并安装（覆盖 /usr/local/bin/eei-pull-deploy.sh 与 /etc/linze-pull-deploy/eei-universe.env）
git clone --depth 1 --filter=blob:none --sparse https://github.com/LinzeColin/MetaDatabase.git /tmp/mdb \
  && git -C /tmp/mdb sparse-checkout set EEI/apps/universe/deploy \
  && sudo bash /tmp/mdb/EEI/apps/universe/deploy/install.sh
sudo bash /tmp/mdb/EEI/apps/universe/deploy/install.sh --check     # 应全是「一致」

# 2. 强制部署一次（首次 tree 哈希口径变了，本来也会重建；--force 保证路由标签也刷新）
sudo /usr/local/bin/eei-pull-deploy.sh run eei-universe --force
sudo /usr/local/bin/eei-pull-deploy.sh status eei-universe
journalctl -u eei-universe-pull.service -n 60 --no-pager

# 3. 线上核对
curl -s https://eei.linzezhang.com/version.txt                                   # 应是合并提交号
curl -s https://eei.linzezhang.com/ | grep -o '<title>[^<]*'                     # 商域宇宙
curl -s "https://eei.linzezhang.com/?subject=00000000-0000-4000-8000-000000000006" | grep -o '<title>[^<]*'   # 商域图谱
curl -sI https://eei.linzezhang.com/structure | head -5                          # 200 text/html，带 CSP
curl -s https://eei.linzezhang.com/build.json                                    # 容器里的前端构建戳
docker stats --no-stream $(docker ps --filter name=eei-universe -q)              # 内存应在 10MiB 量级

# 4. 验收旅程
sudo linze-e2e run EEI.yaml
sudo linze-e2e run EEI宇宙.yaml
```

`/v1/*` 上游仍是 workers.dev；数据接口迁到服务器后，在 `eei-universe.env` 的 `RUN_EXTRA_ARGS` 加 `-e EEI_UPSTREAM=https://…`，重跑 `install.sh` 与 `run --force`。回滚：步骤同 `deploy/README.md`「回滚到 Cloudflare Worker」；旧版静态资源原本也还在 Worker 上，回滚不丢功能。

## 坑

- 容器里 `/_next/*` 找不到的文件会回退上游，而上游 Worker 的 `not_found_handling: single-page-application` 对任何路径都回 200 + HTML（不是 404）。所以「缓存里旧页面引用了已不存在的 chunk」会拿到 200 的 HTML，浏览器按 JS 解析失败。用 `Cache-Control: private, no-cache` 让页面每次重新验证，实际遇到的概率很低；根治要么去掉 `/_next/` 的上游回退（需求明确要求保留，所以没去）。
- nginx `/v1/` 缓存会把 **404 缓存 10 分钟**（既有配置）。本地换数据后要重启容器才清缓存。
- 沙箱里 Docker Hub 对 `node:24-alpine` 返回 429，且容器内不信任出口代理的 CA。验证时用 `--build-arg NODE_IMAGE=`（Dockerfile 暴露了 `NODE_IMAGE`/`NGINX_IMAGE` 两个 ARG）换成镜像站与带 CA 的衍生镜像；服务器上用默认值即可。
- `apps/web` 的 `development-status`、`objects-scope` 两页在构建期读 `../../data/*.csv`，所以 Dockerfile 要 `COPY data`，`WATCH_PATHS` 也包含 `EEI/data`。
- pnpm 版本固定 11.8.0（`EEI/package.json` 的 `packageManager`）；Node 要 ≥24（`engines`）。

# 执行与验收

## 测试节奏

- 每个 Task：只运行与该变更直接相关的 focused tests。
- 每个 Stage 末：运行一次该 Stage 的端到端集成门。
- 冻结 Candidate：运行一次完整测试、静态检查、任务包追踪与恢复演练。
- 上线后：systemd timer/CI 自动运行非阻塞巡检；不以真实时间等待阻塞当前版本。

## 最小真实闭环

```text
真实输入/页面 → Connector → Observation/Relation → L0/L1 → L3 下载
→ R2/OCI/GitHub Release 副本 → PWA 可检索 → 重启后仍可打开
→ 从备份恢复 Fixture → 哈希一致
```

## 证据要求

每项 Acceptance 必须绑定：精确 commit、环境指纹、命令 argv、输入 ID（脱敏）、Expected、Actual、退出码、日志哈希、数据库/对象状态、截图或 API 输出。`UNKNOWN`、`NOT_RUN`、`WAIVED` 均不能折算为 PASS。

## 发布裁决

- 任务包完整性：由 `verification/verify_taskpack.py` 裁决。
- 产品 Candidate：由冻结任务包与精确仓库 commit 的独立 Verifier 裁决。
- 真实平台、真实对象存储、DNS 与生产副作用只能在 Build Last Mile 后裁决；本任务包不得伪造 PASS。

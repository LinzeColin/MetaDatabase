# 运维、恢复与零费用手册

## 日常命令

```bash
bash scripts/start.sh
bash scripts/stop.sh
bash scripts/doctor.sh
bash scripts/backup.sh
bash scripts/restore.sh --dry-run <恢复点>
bash scripts/restore.sh --latest --verify-only
bash scripts/export.sh all
```

部署前可先运行 `bash scripts/install.sh --dry-run`；它只检查 Python、Git、Docker/Compose 和源文件，绝不创建 `.env`、runtime、Secret、配对码、venv、网络或镜像。`bash scripts/doctor.sh --self-test` 同样是零写入静态检查，不连接 Docker、loopback 或外网。真实域名只读探针必须由 Owner 明确执行 `python scripts/deployment_probe.py --domain <域名> --network-confirmed`；默认或 `--read-only` 会返回 `NOT_RUN`。

状态定时器通过 systemd `LoadCredential=` 在每次启动时取得短生命周期的 API Token 文件，并只写 `/var/lib/social-archive/status/social-archive.json`；长期 source secret 不向宿主 service 直接开放。Core 容器内端口仍为 `8765`，但宿主机只用 `.env` 的 `SOCIAL_ARCHIVE_CORE_LOOPBACK_PORT` 映射到 `127.0.0.1:18765`；`social-archive-status-web.service` 用同一受限账户只读该文件、绑定 `.env` 的 `SOCIAL_ARCHIVE_STATUS_PORT=18780`。生产中 Core 的 `/var/lib/social-archive`、`/import` 与 `/vendor-output` 必须分别由 `SOCIAL_ARCHIVE_DATA_HOST_PATH=/var/lib/social-archive`、`SOCIAL_ARCHIVE_IMPORT_HOST_PATH=/var/lib/social-archive/import`、`SOCIAL_ARCHIVE_VENDOR_OUTPUT_HOST_PATH=/var/lib/social-archive/vendor-output` 绑定，确保 Core、CLI、备份、复制、Private-Database 同步和状态服务操作同一数据面；禁止 Docker named volume 或项目内 `runtime/` 替代。Core 以 uid `10001` 运行并在入口设置 `umask 0007`；CLI Sidecar 是 uid `10002`，必须通过 `SOCIAL_ARCHIVE_HOST_DATA_GID=$(id -g socialarchive)` 加入共享数据根的 setgid 组，而不是得到任何复制凭据。`prepare_systemd_host.sh --apply` 只建立浅层、setgid 的 `10001:socialarchive` 数据目录，绝不递归重设既有用户对象的所有权；已有 SQLite 不满足共同写入条件时会 fail closed，要求先做受控迁移。若已存在 `/etc/social-archive/social-archive.env`，准备脚本还会逐项拒绝任何“宿主机非 Secret 配置有值、`.env` 却为空”的覆盖，防止误清空 R2/OCI/age/配额等运行配置；先把这些非 Secret 值受控迁入 `.env`，再执行 apply。R2、OCI 和 GitHub Vault 凭据不会挂载给 Core；复制/冷备/status unit 仅按需通过 `LoadCredential=` 取得临时副本，已配置的 Vault `github_token` source 必须保持 `root:root 0600`。状态 unit 不使用 `StateDirectory=`，以免 systemd 重置共享数据根的所有权。`status.linzezhang.com` 是既有站点，所以 Tunnel 只把 `/social-archive.json` 与 `/social-archive-health` 路由到此只读服务，其余路径继续到本机 Traefik `127.0.0.1:80`；它不开放 OVH 公网端口且不接受写请求。首次通过 `social-archive-status.service` 生成状态投影；再启用 `social-archive-status.timer` 每五分钟刷新。部署时安装全部 `deploy/systemd/*.service`/`*.timer`，执行 `systemctl daemon-reload`，并启用 `social-archive.service` 与 `social-archive-status.timer`。本地自检只验证这个合同，不能把真实 Tunnel、DNS、TLS 或公网可用性报为已经上线。

生产环境重新生成一次性配对码时，在 `/opt/social-archive` 以已授权身份运行 `sudo bash scripts/start.sh`。该脚本会保留既有受管 Secret 的所有权/权限，并强制重建非 root Core/Worker，以确保 Docker Compose file-secret 重新挂载新文件 inode；不要只替换配对码文件后假定旧容器已自动读取新码。

## OVH systemd 宿主机准备

生产源必须先以精确路径部署在 `/opt/social-archive`，并完成正常 `install.sh`（含 `.env`、`.venv` 与 `runtime/secrets`）。先运行：

```bash
bash scripts/prepare_systemd_host.sh --dry-run
```

这一步只核对源合同，绝不写系统目录、创建账户、读取凭据内容、启用/启动 Docker、systemd、Tunnel 或云服务。确认目标、回滚边界和当前目录后，Owner 才能以 root 显式运行 `--apply`。该命令只会：创建受限 `socialarchive` 系统账户（如不存在）、确认 `.env` 中三条 bind path 与 `SOCIAL_ARCHIVE_HOST_DATA_GID=$(id -g socialarchive)` 均精确匹配、建立 Core/CLI/受限宿主维护服务共享的浅层 setgid 数据目录、生成不含 Secret 值或 source secret 路径的 `/etc/social-archive/social-archive.env`、备份已有 `/etc/social-archive`/相关 unit 到 `/var/backups/social-archive/`、安装仓内 unit 并执行 `systemctl daemon-reload`。它不会重设长期 secret 的所有权或权限；R2、OCI、GitHub Vault 和 API token 由对应 unit 的 `LoadCredential=` 在启动时取得短生命周期副本，已配置的 Vault `github_token` 必须保持 `root:root 0600`。它**不会** enable 或 start 任何 unit、Docker、cloudflared 或云资源。

随后才由已授权的 Owner 按最小范围启用 `social-archive.service` 与 `social-archive-status.timer`，核验 `social-archive-status-web.service`，再配置 Tunnel/Access/WAF。若需回滚，先停用新 unit，再从该次输出的备份目录恢复 env 和 unit 并 `systemctl daemon-reload`；不要覆盖 Runtime、Secret 内容或 Private-Database。

专用 Tunnel 不修改既有 `cloudflared.service`。它使用 Cloudflare 托管的远端 ingress：仓内渲染器只生成非 Secret JSON 请求体，由受控 Cloudflare API 写入新 Tunnel 后再读回核验。Tunnel Token 仅写入服务器 `/etc/social-archive/social-archive-cloudflared.env`（0600），`social-archive-cloudflared.service` 只从该文件读取变量、不会在 unit 中保存值；回滚时停用该 unit 并恢复 DNS/Access/WAF 的本轮前快照。

首次安装会在 root 的受控部署路径预置 `runtime/import` 与 `runtime/vendor-output/{cli,xhs,kuaishou,douk}`：Core 的 uid/gid 是 `10001`，CLI sidecar 是 uid `10002` 但共享 gid `10001`，这些 bind mount 使用 setgid 的 `2770`。这是避免 Docker 对宿主机新目录保留 root 所有权、导致无特权容器无法启动的必要边界；不要为了修复权限把 Core 或 Sidecar 改为 root，也不要把目录放宽为全局可写。

## 标准 Markdown / JSONL 导出

`bash scripts/export.sh all` 只写派生导出目录（默认是 `SOCIAL_ARCHIVE_EXPORT_ROOT`），不改写 Canonical Store。每次输出：

- `obsidian-vault/`：每条内容一个 Markdown，含前置元数据、原始链接和已保存正文；
- `library.jsonl`：稳定排序的便携记录，每行一个内容及其代表关系；
- `notion-import.csv`、`bookmarks.html`、`archivebox-urls.txt`、`feed.json`；
- `EXPORT_MANIFEST.json`：导出快照 SHA-256 与清单。

同一快照再次导出会返回 `noop`，不因时间戳而重写文件；导出失败不影响已保存内容或后台归档任务。

## 运行不变量

- API 与 Worker 可以重启；任务通过 SQLite Runtime Journal 恢复。
- 完成态事实必须进入 Private-Database，媒体对象必须有 R2 主副本。
- 每个对象记录 R2、OCI、GitHub Release 三个副本状态和哈希。
- `status.linzezhang.com` 只展示只读摘要，不保存权威状态。
- 发布前必须在 Cloudflare 控制台核验 UI Access、独立 API Host、Tunnel loopback route、WAF/Rate Limit 和无 Bearer 业务路由的 401。源码和本地 fixture 只能证明合同，不能替代该真实验收。
- Runtime 不依赖开发 Agent、聊天线程、人工保活或 macOS launchd。

## 配额与降级

| 存储 | 软门 | 硬门 | 硬门动作 |
|---|---:|---:|---|
| Cloudflare R2 | 8 GiB | 9.25 GiB | 暂停新 L3；L0/L1 继续 |
| OCI | 16 GiB | 19 GiB | 暂停镜像并告警，不删除 R2 主对象 |
| GitHub Release 加密包 | 8 GiB | 9.25 GiB | 暂停新包，R2/OCI 不受影响 |
| Git 工作树 | 0.8 GiB | 1 GiB 目标 | 拒绝媒体与大对象进入 Git history |

任何接近供应商实际免费限制的值都必须由部署前探针重新读取并取更低值；任务包数值是安全预算，不是供应商合同保证。

## 恢复顺序

1. 只读验证恢复点、清单、签名/哈希和目标路径。
2. 新建空目录恢复 API 同步事实快照，不覆盖或创建 Private-Database 工作树；`restore.py` 会拒绝 R2/OCI 收据不完整、密文哈希错误、tar 路径穿越和缺少三副本对象收据的恢复包。若本机备份目录已经丢失，可显式运行 `python scripts/restore.py --latest --from-store r2 --verify-only`（或 `oci`）；它只读受验证的远端 `recovery.json` 和同一 age 密文。
3. 使用 `python scripts/rebuild_runtime.py <恢复目录> --target <全新 sqlite 路径>` 重建 Runtime SQLite 与 FTS；目标已存在时必定拒绝覆盖。
4. 按 R2 → OCI → GitHub Release 优先级恢复缺失对象。
5. 对 Fixture 运行端到端读取、关系、对象哈希和重启验证。
6. Owner 确认后才允许切换当前部署；失败时删除新目录，不改变旧部署。

## 单平台故障

Connector 连续失败达到阈值后进入 `degraded`，只停止该 Connector 的自动任务；通用当前页采集、其他平台、搜索和导出保持可用。恢复探针成功两次后才自动解除熔断。

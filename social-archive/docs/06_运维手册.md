# 运维、恢复与零费用手册

## 日常命令

**先分清你在哪台机器上——两套命令不能混用。**

### 本机自建 / 开发机

```bash
bash scripts/start.sh
bash scripts/stop.sh
bash scripts/doctor.sh
bash scripts/backup.sh
bash scripts/restore.sh --dry-run <恢复点>
bash scripts/export.sh all
bash scripts/load_extension_instructions.sh   # 装/更新浏览器扩展：先自检，再打开扩展目录
```

装载扩展这一步只能人来做（`chrome://extensions` 是浏览器设置页，自动化进不去；
Chrome 137 起也不再支持 `--load-extension`）。上面那条命令把能自动的部分做完——
跑一次扩展预检，再把目录在访达里打开，剩下三次点击留给你。

### 生产（OVH，systemd 托管）

生产的 Core 由 `social-archive.service` 管着。**不要在生产上跑 `stop.sh`**
——它执行 `docker compose down`，而 systemd 会把容器再拉起来，你会看到
一个自己反复重启的服务，并以为是故障。

```bash
systemctl status social-archive.service
sudo systemctl restart social-archive.service
bash /opt/social-archive/scripts/check_durability_units.sh   # 保命的 unit 有没有启用
sudo journalctl -u social-archive-replication -f                   # 复制真的在跑吗
```

### 生产上跑的，是不是仓里这一份

`/opt/social-archive` 不是 git 检出，**那台机器上没有 `git status` 可问**。
在开发机的工作树里跑（只读，只 ssh 过去算哈希）：

```bash
python3 scripts/check_production_matches_the_repo.py --explain-differences
```

**要比的是三份，不是两份**：

    仓 ←→ 主机 /opt/social-archive ←→ **镜像里的 /app**

第三份容易被漏掉：容器里的 `/app` 是**烤进镜像的**，不是主机目录的绑定挂载
（只有 `/run/secrets/*` 是）。所以**改主机上的脚本，容器里那份纹丝不动**，
直到镜像重建——这正是上面「`systemctl restart` 不会重建镜像」的另一面。
只比前两份会得出一个安心但不成立的结论。

| 分类 | 意思 | 要紧程度 |
|---|---|---|
| `only_on_production` | **没人知道从哪来的代码，正在生产上跑** | 最要紧，会让这道门红 |
| `container_is_running_older_code` | **服务执行的不是你以为的那一版**；要重建镜像 | 要紧，会让它红 |
| `logic_differs` | 主机与仓逻辑不同——没同步，或者有人手改过 | 要紧，会让它红 |
| `comment_only` | 只差注释 | 不红，但也不当成完全一致——注释也是交接的一部分 |
| `only_local_not_deployed_yet` | 新写的还没发 | 最轻 |

2026-08-05 首次实测：`only_on_production` 是**空的**；当天把一个修好的脚本
放到主机后在容器里跑，跑的还是旧的——`container_is_running_older_code`
那一栏就是那次撞出来的。部署脚本第 8 道门只逐字节核了**扩展包**那一个文件，
其余一百多个源文件此前从来没有任何东西核过。

### 更新到新版本（**`systemctl restart` 不会重建镜像**）

拉了新代码之后只 `systemctl restart social-archive.service` 是**不够的**：
它的 ExecStart 是 `docker compose up -d core-api core-worker`，没有 `--build`，
容器会用**旧镜像**重建，代码改动一个字都没进去。

而它看起来完全正常——服务起来了、`/health` 200、日志没有异常。
你会以为新版已经生效，然后发现**那个 bug 还在**。C-T00-01 的根因修复就在
`sidecars/cli-tools/Dockerfile` 里：不重建镜像，CLI Sidecar 依旧读不到自己的
密钥，界面依旧永远「同步中」。

**别在生产上 `git pull`。** `/opt/social-archive` **不是 git 检出**
（实测：`git rev-parse` 报 `not a git repository`）。代码是从开发机
**rsync** 上去的——这一段原来写着 `cd /opt/social-archive && git pull`，
照着敲第一步就报错。`update.sh` 早在 2026-08-04 就按实际情况改对了
（不是 git 检出就跳过干净度检查），**只有这份手册一直没跟上**。

正常升级从**开发机**发起：

```bash
# 在开发机的工作树里
bash scripts/deploy_to_production.sh       # rsync 源码 → 重建镜像 → 重建容器 → 逐道门检查
```

只想在生产上就地重建镜像（比如只改了 Dockerfile、代码已经同步过去了）：

```bash
# 在生产上
cd /opt/social-archive
sudo systemctl start social-archive-backup.service   # 先取快照（走定时器同一条路）；回滚唯一诚实的做法是恢复快照
sudo bash scripts/update.sh               # 重建镜像 → 重建容器 → 健康检查
```

`update.sh` 在**开发机**上会先拒绝工作树不干净时继续；在生产上它会说
「当前目录不是 git 检出（生产就是这样），跳过干净度检查」——那句话是对的，
不是出错。最后它会明确告诉你镜像已重建。

### 生产上有没有明文密钥落进日志

密钥最可能泄漏的地方不在仓里，是日志——某个脚本顺手把环境变量打出来，
或者异常回溯里带着令牌。在开发机的工作树里跑（只读）：

```bash
python3 scripts/scan_production_for_leaked_secrets.py --days 14
```

它只报 文件:行号 / 种类 / **值的长度**，从不打印值本身——
一个把密钥打给你看的检查器，自己就是下一个泄漏点。

2026-08-05 首次实测：运行数据 2119 个文件 + 五个单元近 14 天共 3545 行日志，
**0 处命中**。

> **这条在那天之前查不了**，不是没查：两道密钥扫描门当时都认不出
> Notion / Obsidian / R2 私密访问密钥，以及 **age 私钥**——占位符过滤按前缀
> 跳过 A 开头的值，而 age 私钥永远以 `AGE-` 开头。
>
> **0 命中的意思是：已知形状里一个都没有。那不等于一定没有。**

### 回滚（**先确认回滚点还在，再谈回滚**）

这条命令此前只出现在部署脚本跑完时的输出里——**终端一滚就没了**。
半夜要回滚的人在文档里找不到它，所以搬到这儿。

> **主机名别写死在脑子里。**（2026-08-13 查出来的）
> 这一节原来写的是 `ssh linze-ovh`，而那台机器**已经连不上了**（实测超时）。
> 半夜照着敲的人会挂在超时上，还以为是自己网络的问题。
> 真源只有一个：`deploy/PRODUCTION_HOST`（这份文件里写着当前那台机器的名字）。
> 下面每条命令都先从它取，**别把机器名记在脑子里或抄进命令**：
>
> ```bash
> H="$(cat deploy/PRODUCTION_HOST)"
> ```

**第一步永远是确认那个镜像还在**，别直接敲回滚：

```bash
ssh "$H" "sudo docker image inspect -f '{{.Id}}' social-archive/core:rollback"
```

报错说 No such image，就是**没有回滚点**——这时候别再试那条 tag 命令，
它只会失败。往下看本节最后那一段（没有回滚点的时候怎么办）。

有的话，回滚就是一行：

```bash
ssh "$H" "cd /opt/social-archive && docker tag social-archive/core:rollback social-archive/core:$(cat VERSION 2>/dev/null || echo 0.0.0.70) && docker compose up -d core-api core-worker"
```

（那个版本号要填**当前跑着的那一版**——`curl -s https://social-archive-api.linzezhang.com/health`
里的 `version` 就是。写错版本号不会报错，只会把标签打到一个不存在的名字上。）

实测过一次：29 秒，三条路由全 200，内容 193 条未动，会话没被踢
（见 `evidence/T18/ROLLBACK_DRILL_ON_PRODUCTION.json`）。

**回滚点什么时候会消失：**

  · 每次部署会把它重新钉到部署前正在跑的那个镜像上——所以正常情况下它总在；
  · 而它占 1.06GB。**磁盘紧张时它是最容易被删掉的东西**——
    2026-08-05 就是我自己删的（当时可用空间 3.2G，构建被 5G 的门挡住）。
    删了之后到下一次部署成功之前，**这台机器没有回滚点**。

**没有回滚点的时候怎么办**：回滚唯一诚实的做法是恢复快照
（生产上由 `social-archive-backup.timer` 每天取的那种），照本文档后面那节 *恢复顺序* 走。
镜像回滚只能退代码，退不了数据；快照两样都能退。

### 保命的三个 timer（**装好之后必须显式启用**）

`prepare_systemd_host.sh` 按设计**不启用**任何 unit（装好 → 验收 → 显式启用）。
2026-08-04 实测：生产上 backup / replication / private-database-sync
三个 timer **一直是 disabled，journalctl 90 天内全是 No entries**，
结果是 549 个制品里 530 个一个异地副本都没有。

```bash
sudo systemctl enable --now social-archive-backup.timer \
                       social-archive-replication.timer \
                       social-archive-private-database-sync.timer
bash /opt/social-archive/scripts/check_durability_units.sh
```

## 运行不变量

- API 与 Worker 可以重启；任务通过 SQLite Runtime Journal 恢复。
- 完成态事实必须进入 Private-Database，媒体对象必须有 R2 主副本。
- 每个对象记录 R2、OCI、GitHub Release 三个副本状态和哈希。
  **注意这是目标，不是现状**：它只有在上面三个 timer 启用之后才成立。
  当前是否成立，用 `/v1/status` 的 `storage.completion` 或
  `check_durability_units.sh` 现场核，别假定。
- `status.linzezhang.com` 只展示只读摘要，不保存权威状态。
- Runtime 不依赖开发 Agent、聊天线程、人工保活或 macOS launchd。

## 配额与降级

| 存储 | 软门 | 硬门 | 硬门动作 |
|---|---:|---:|---|
| Cloudflare R2 | 8 GiB | 9.25 GiB | 暂停新 L3；L0/L1 继续 |
| OCI | 16 GiB | 19 GiB | 暂停镜像并告警，不删除 R2 主对象 |
| GitHub Release 加密包 | 8 GiB | 9.25 GiB | 暂停新包，R2/OCI 不受影响 |
| Git 工作树 | 0.8 GiB | 1 GiB 目标 | 拒绝媒体与大对象进入 Git history |

任何接近供应商实际免费限制的值都必须由部署前探针重新读取并取更低值；任务包数值是安全预算，不是供应商合同保证。

## 恢复顺序

**先说能跑的那一条。** **出事的时候东西拿得回来吗**——这个问题，仓里已经有脚本
每次部署都真答一遍（下载 → 解密 → 打开 → 判，不是读登记表）：

```bash
# 在开发机上跑；它会 ssh 到生产去真取一次回来
python3 scripts/check_the_backup_can_actually_be_restored.py
```

> **不要在生产上直接敲 `bash scripts/restore.sh`。** 实测（2026-08-13）它会回
> `{"status": "BLOCKED_ENVIRONMENT", "message": "恢复节点缺少 SOCIAL_ARCHIVE_AGE_IDENTITY_FILE"}`
> ——解密身份来自 systemd unit 的 EnvironmentFile，不在 shell 里。
> 上面那个脚本正是用 `systemd-run --property=EnvironmentFile=…` 把环境带进去的，
> 所以它跑得通而手敲跑不通。

下面六步是**恢复本身的顺序**（上面那条只验"取得回来"，不动现有部署）：

1. 只读验证恢复点、清单、签名/哈希和目标路径。
2. 新建空目录恢复 Private-Database 快照，不覆盖现有工作树。
3. 重建 Runtime SQLite、FTS 与 PWA Projection。
4. 按 R2 → OCI → GitHub Release 优先级恢复缺失对象。
5. 对 Fixture 运行端到端读取、关系、对象哈希和重启验证。
6. Owner 确认后才允许切换当前部署；失败时删除新目录，不改变旧部署。

## 单平台故障

Connector 连续失败达到阈值后进入 `degraded`，只停止该 Connector 的自动任务；通用当前页采集、其他平台、搜索和导出保持可用。恢复探针成功两次后才自动解除熔断。

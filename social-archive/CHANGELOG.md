## v0.0.0.52 — 播报写进了证据文件，而没人看见；钉它的那条测试还是空的

上一版把「56 篇标题是播放进度」做成播报而不是门（它是他库里已经存在的数据，
做成门在他重新同步之前永远变不绿）。**但那条播报只写进了证据 JSON，
部署的 8.67 一个字都没印**——记下来了、没人看见，
和「判据没有调用方」是同一种毛病。现在它跟着那四个计数一起印出来。

**顺手给它补的那条测试，自己是空的。** 它这么切窗口：

    source[source.index("problems…"):source.index("print(json.dumps(")]

而文件里**更早**就有一个 `print(json.dumps(`（库不存在那一支的 SKIPPED 输出），
于是右端 < 左端、切出空串，`not in ""` 恒真——**这条测试永远绿**。
不是读代码看出来的：把播放进度塞回 `problems`（做成门），测试照样十条全过，
才发现它根本够不着要守的东西。改成 `rindex` 并只看 append 那几行，
反例这才当场红。（`my-checkers-are-mis-cut-six-times-in-one-day` 又一次。）

两条反例现在都成立：删掉播报 → 红；把它做成门 → 红。

## v0.0.0.51 — 产品在存他的浏览历史，而说明书只写了「收藏夹」

**打开他 Obsidian 库随手看一篇，看到的是这个：**

    url: "https://www.bilibili.com/video/BV1H4N2ezEob/…"
    author: null
    relation_types: ["history"]
    collections: ["综合视频直播专栏 更多筛选 清空历史批量管理全部时长10分钟以…"]

    # 34:04/42:37

标题是**播放器上的时间**，collections 是**页面筛选栏那一整段文字**。
全库数了一遍：193 篇里 **56 篇**是这个样子，**全部来自 history 那条路**。
而每一道门都是绿的——这类标题「以数字开头」，那一条恰恰被判成正常
（「10万个冷知识」那次的教训，反过来咬了一口）。

**顺着它查出更要紧的一件事。** `account_sync.py` 里 bilibili 采的是
`["favorite", "watch_later", "history", "like"]`——**它连浏览历史和点赞一起存**。
而说明书 B站 那一行从头到尾只写「你的收藏夹（全部收藏夹，逐个读）」。
数了他库里的关系类型：**条数最多的两类是历史和点赞，收藏夹反而不是最多的那类。**

**这不是措辞问题：产品在归档他看过什么，而说明书没告诉他。** 他完全可能不想要。
说明书那一行改成「不只是收藏夹：收藏夹、稍后再看、**浏览历史**、**点赞** 都会读进来」，
并加了一段说清「不想要的话这一条要告诉我，那是改产品的事，不是你去点什么」。

**那 56 篇做成播报，不做成门。** 它是他库里**已经存在**的数据，不是这次弄坏的；
做成门就在他重新同步之前永远变不绿，而那种红只会逼下一个人绕过整道检查
（`a-red-that-can-never-turn-green-is-not-a-signal`）。真因在取数侧，
而验证修复要他登录后的页面——我这边看不到，所以**说出来，不拦**。

顺带：我在说明书里写了「历史 71 条、点赞 69 条」，**被那道门当场打红**——
「散文里不许冻一个会过期的数字，同步一次就成假话」。改成只说形状，数字让他看资料库那一列。

## v0.0.0.50 — 同一份说明书，一天里两个方向各错一次

昨天补的那道反方向门查出了**少说**（第一步会撞到 Cloudflare 验证页，说明书没写）。
今天顺着同一条线量下去，发现同一份说明书还**多说**了一句：

    这是老版本取数时没取到……**重新同步会把它们补上**。

那是一句**无条件承诺**，而我只证得了其中一半。实测：

    B 站真接口，5 条里 5 条都带 author_name 和 published_at   ← 那 101 行补得上
    抖音／小红书／快手是从**页面自己发的响应**里读的           ← 页面给了才补得上

而我这边看不到**。所以那句话改成分档的实话：B 站那部分照写，其余明说
「这一条我没法替你打包票」。（补得回来的机制本身是查过的：
`COALESCE(excluded.author_name, …)` 补空不覆盖，`stable_id` 让同一条算出同一个 id，
所以是补齐而不是变成两条。）

**这一类没有门管，而且不该硬做一个。** 那道门查按钮字、地址、平台表，
查不到承诺句；而「这句承诺证得了吗」要看外部系统给不给，机器判会大量误报，
**一道会误报的门比没有门更坏**。已写进 AGENTS.md 那张症状表旁边：
说明书里每出现一句「会…」，先分清哪一部分是量过的、哪一部分取决于我看不到的东西。

前言也跟着补了一句：那道门查的是正方向，另有一道查反方向——
**只有正方向那一道时，少说可以一直是绿的**。

顺带一个自找的红：前言里我写了个空的 `>` 行，`build_guide_page.py` 不认这种写法，
**它拒绝生成一份糊的页面**而不是硬转——这是它该有的样子。

## v0.0.0.49 — 那个新演练最要紧的一句话，是写着的不是量出来的

`real_platform_into_archive_drill.py` 昨天刚落地，它**跑在生产机上、而且真的
往档案馆写东西**。它敢这么跑，全靠一条边界：数据根在一次性容器的 tmpfs 里，
**碰不到他那 193 条**。

而那条边界此前只出现在三个地方——文档注释、报告里的 `boundary_zh`、清单那一行——
**三处都是「写着」，没有一处是量出来的**。我自己手工数过一次（跑前跑后都是 193），
可手工数不会在下一次部署时自己发生。`self-report-is-not-evidence`：
能出示的就要出示，而这一条恰恰是这个演练最不能出错的地方。

现在它跑前跑后各数一次他的库，报告里带着 `his_library_before / after`：

    他的库 前 193 → 后 193      ← 实测，写进证据

三种情况都会红：数不出来（ssh 断／容器没起／表名变了）、前后不一致、
以及 `None` 被当成相等——第三种单独判，不参与比较。
反例：把跑后那个数注入 +1，当场红并把两个数原样列出来（193 → 194）。

清单那一行也跟着改了措辞：不再写「碰不到他的库」，改成
**跑前跑后各数一次他的库，条数变了就红**——**是量过，不是写着**。

（`from_zero_drill` 有同样形状的一句，这轮没动它：它跑在一次性容器里、
连生产 API 都不打，隔离比这个更强；不顺手扩大改动面。）

## v0.0.0.44 — 挂了四天的「只有 Owner 能授权」，是我们自己测错了

说明书、部署播报、演练清单、判据文案，四处都写着同一句：第三份备份验不了，
**那把恢复令牌看不见 `LinzeColin/Private-Database`，只有 Owner 能去 GitHub 加授权**。
这一版把它推翻了——**授权一直都在**，两个原因都在我们这边：

| 表面现象 | 真因 |
|---|---|
| 「缺少 gh 或 GitHub 令牌」 | `.env` 指的 `/run/secrets/github_token` 是**容器内**路径，宿主机上没有；按文件名回退落到 `runtime/secrets/github_token`——那把确实看不见那个仓。而同机的 `github_markdown_token` 对它是 **ADMIN**（`gh repo view` 实测），备份服务自己就是靠单元里 `LoadCredential` 映射到它才每天写得成第三份 |
| 第三份「没有收据」 | 三份写齐只发生在**每天 03:28 那次 backup.service**；r2/oci 另有每 15 分钟一份。判据一律取「最新那批」，于是 github 永远落在一批根本没有它收据的快照上——**一条永远变不绿的红** |

改完实测：**三份全部真取回来**（下载 → 解密 → 打开 → 判），各 193 条；
8.9 从 2/3 变 **3/3**。说明书那句从「今天能确认拿得回来的是 2 处」改成 **3 处**，
并去掉了那句「这一条只有你能开」——**它一直在让他以为有件事等着他做**。

判据现在照抄备份单元那行 `LoadCredential` 当真源，读不到就明说
（`GITHUB_CREDENTIAL_MAPPING_NOT_FOUND`），**不许猜第二把令牌**；
每个 store 各挑「最新的、带它自己收据的那一批」。

**两条跨层的教训，都是被自己的调试骗过之后才看清的：**

- `%d` 只在单元文件里展开。经 `systemd-run --property=Environment=` 传进去是字面量，
  程序拿到的就是字符串 `%d/github_token`。r2/oci 侥幸没事，是因为 `_s3_config`
  有按文件名回退的路；github 那条没有，于是报「缺少 gh 或令牌」——一句指向错方向的话。
- **ssh 的命令串会被远端登录 shell 先展开一次。** 第一版覆盖写成 `GH=$(...)` 再
  `[ -n "$GH" ]`，那一层把 `$GH` 展成空、覆盖静默失效；而我去查它的时候，
  **本机** shell 又把调试命令里的 `$GH` 吃掉一次，连着两次让我看见空值。
  路径改成在 Python 里算好、以字面量拼进命令，一层变量都不留。

顺带：`sed -n "s/…/p"` 经三层引号之后收到的表达式**开头就是一个字面双引号**，
直接报 unknown command——换成 grep+cut，不需要任何引号。
以及那三条把「2 处」写死的测试改成**从说明书原文现读**：它们要守的是
「多说少说都会被抓」，不是某一个具体的数。

## v0.0.0.43 — 另外两格也量完接上了；抽样差点变成一句假话

上一版把运行库那一格接进了部署。剩下两个恢复演练还挂在**靠人记得**那一档，
理由是「跑一次的代价没量过」。这一版把代价量了，量完就没得商量了：

| 演练 | 实测 | 处置 |
|---|---|---|
| `restore_private_database_drill.py` | **2 秒** | 每次部署全跑 |
| `disaster_recovery_drill.py` | 1.3 秒/制品，全量 552 个约 **12 分钟** | 每次部署抽 **25 个（32 秒）** |

三棵备份树加起来一次 **50 秒**，实测全绿：运行库 r2/oci 各 193 条、
Private-Database 的 fact 包、索引与制品对得上。

**差点在这里放出一句假话。** `--limit N` 原来是 `ids[: N]`——确定性地取头 N 个。
单独手跑时无所谓，接进每次部署那一刻它变致命：552 个制品里永远只有同样的 25 个
被验过，另外 527 个一次也不会被碰到，而日志上写着 25/25 全过。
现在起点由 `--offset` 决定并环形绕回（按版本号取，每发一版挪一格），
报告里把窗口和分母一起打出来：`552 个里的 25 个（窗口 498–523）——不是全量`。
判据钉着这一条：把挪窗口改回取头 N 个，两条测试当场红。

**再加一道：一个版本号只许对应一份插件。**
上一版查账时发现 VERSION 停在 0.0.0.41 期间真部署了 11 次。那次侥幸
（`apps/browser-extension/` 零提交），而出事的样子这个仓记过——一天发 6 个不同的包
全标 v0.0.0.22。这次去读了原文核实真因，它就在 `extension-install.html` 里：

## v0.0.0.35 — 缓存戳改成由内容算，并证明源站的 Cache-Control 治不了这件事

**先说实测到的根因**（另一个会话在自己的 zone 上先发现，我在这边复现了）：

    源站（生产机上打回环 127.0.0.1:18765）  HTTP/1.1 200 OK   ← 一个 cache-control 都没有
    公网（经 Cloudflare）                   cache-control: max-age=14400

那 4 小时是 **Cloudflare 的 Browser Cache TTL** 加的，**源站的头会被它盖掉**。
也就是说在 nginx / 应用层设 `no-cache` 是无效的，**换缓存键是唯一可靠的手段**，
而键必须永远正确、不能靠人记得。（首页是 `cf-cache-status: DYNAMIC`，不缓存，
所以他每次都拿到新 HTML，戳一变必然回源——这条也实测过。）

0.0.0.30 把戳改成跟着 `VERSION` 走，修好了「戳永远不动」，
**却留下一扇同形状的门**：改了 `apps/pwa/` 却忘了升版 → 戳不动 → 他还是拿旧的。
（`apps/browser-extension/` 有「改了就必须升版」那条判据，`apps/pwa/` 没有。）

现在 `scripts/stamp_pwa_assets.py` 按内容算 `sha256[:8]`，一个戳管全部资产：
首页每个 `/assets/…`、sw.js 的缓存名与预缓存清单、app.js 里注册 SW 的 URL。
哈希前先把所有 `?v=…` 归一成 `?v=`，否则写进去的戳会改变下次算出来的戳、
永远不收敛（判据 `test_the_stamper_converges` 钉着这一点）。
`bump_version` 不再插手这三处——它和内容派生的戳会打架。

部署第 **0.5 步**（**在构建之前**）跑 `--check`，对不上就中止。
实测反例：只往 styles.css 追加一行注释、不重新打戳 → 退出 1、部署中止。
**这个反例在跟着版本号那版是抓不到的。**

另外两处旧判据（`test_pwa_asset_version_is_not_stale`、SW 那条）也改成对内容哈希。

## v0.0.0.30 — 前端资产的缓存戳跟着版本走（不然发了也到不了他浏览器）

    navigator.serviceWorker.register("/assets/sw.js?v=007-r2")   // 连 SW 自己的更新都要等 CDN

判据 `test_a_changed_extension_must_change_its_version.py` 从此盯着这件事：
VERSION 最后一次变动之后只要有提交动过 `apps/browser-extension/`，它就红。

而**手势不跨 `sendMessage`**——MV3 的 service worker 里永远拿不到它。
用发布包在真 Chrome 里量过三种情形：service worker 直接调、
service worker 处理**带手势发出的消息**、页面里调（只有最后一种成功）。

## v0.0.0.22 — Reddit / Instagram 打开了：7 个平台；以及识别器一直在丢标题和作者

### 先说那个缺陷，它伤的是已经上线的平台

按形状认列表的识别器，第一版只看数组元素**自己身上**的字段。
拿三家真实的响应形状去试认，**三家全灭**，理由一模一样
「只有 0% 的元素带得出 id」——因为 id 根本不在元素身上，在包了一层的对象里：

    Reddit     children[].data.id
    Instagram  items[].media.pk
    X          entries[].content.itemContent.tweet_results.result.rest_id

**而这不只是「少认几个平台」。** 小红书自己的条目就是这个形状：`id` 摊在外面，
`display_title` / `user.nickname` 在 `note_card` 里。照第一版：id 找得到，
所以照样入库；标题和作者取不到，**全存成 null**。
也就是说真站上会进来一批只有网址的条目，而全部判据是绿的——
夹具里的条目全是我摊平了写的，所以谁也没抓到。

改法是限深搜索 + 两条收紧：id 的**路径要一致**（不是「每条都有 id」，
是「每条的 id 在同一个位置」），而且**挖到壳里去的必须另有标题或作者佐证**
——`id` 太常见，挖五层几乎能在任何数组里挖出一个，埋点数组会被认成收藏。
反证跑过：改动前那批条目 title/author 全 null，改动后全对。

新增取址顺序：条目自带绝对网址 → 相对路径拼本站域（Reddit 的 permalink）

每条还记下 `derived_by`，演练会核对它——因为「取来的」和「拼出来的」
条目数完全一样，光数数看不出来，而拼错的网址会安静地进档案馆，
半年后点开才发现全是 404。

## v0.0.0.20 — 升一个补丁版本就把所有人锁在门外

资料库判「这个插件还能用吗」用的是 `version === PRODUCT_VERSION`

全被判成不兼容，同步、保存、连接全被挡住，直到用户手动去覆盖文件。

2026-08-06 这一天升了 19 个版本，**每一次都会把他整个锁在外面**。

**却没动这条让它变致命的相等判据**。修了症状，留着病根。

改成「不低于一个下限」。下限 `MINIMUM_EXTENSION_VERSION` 由服务端下发，

界面文案、标签页行为、筛选框这类改动一律不动它——
那些值得提示「有新版本」，不值得把人挡在外面。

现在定在 `0.0.0.9`：那是整条链第一次真的能跑通的版本（在它之前没有 B 站
取数路，也没有登录态确认，连账号都建不起来）。他手上的 0.0.0.7 低于它，
所以**仍然需要更新一次**——这一次是真的该更新。

版本比大小逐段按数字比：字符串比会说 `0.0.0.9 > 0.0.0.10`，
而这一天正好跨过那个边界。

真 Chrome 四种情形都量过：没装 / 版本正好 / **不是最新但够用（不再被拦）** /
低于下限（照旧拦住并讲怎么换）。

## v0.0.0.18 — 后台死了，健康检查照样说一切正常

上一版部署被打断，留下的状态是 core-api 起来了、**core-worker 卡在 Created
没启动**。而 `/health` 由 api 提供，它照样回 `"status": "ok"`。
**从外面完全看不出后台没在跑**，同步任务只会静静积压，
而每一处显示都说服务是好的。

这正是这个产品一直在防的形状，部署脚本的文件头写着同一件事：
「只给前者，容器 /health 照样 200 而业务路由一律 401，界面永远『同步中』」。
那次是密钥属组，这次是 worker——**同一个盲区，换了个位置**。

修法是一行心跳：worker 每轮循环写一次时间戳（**空转的那一轮也要写**，
否则「闲着但活着」和「死了」在数据上分不开），`/health` 拿它和现在比。
「从来没露过面」与「露过面但很久没动」分开报——前者多半是刚部署完还没起来，
后者才是挂了；合成一个布尔值会把刚部署也报成故障，那种门很快会被人忽略。

部署回读也加了这一条，因为**部署当场正是它最容易发生的时刻**。

## v0.0.0.10 — 收藏夹的名字不再被丢在地上；顺带堵掉一条会删数据的路

- **收藏夹的名字读到了却没送出去。** 服务端建收藏夹记录的条件是
  `if batch.collection_name:`，而 B 站那条路一次读完全部收藏夹、批次级
  `collection_key` 是空的，名字就无处可放。结果：`platform_collection`
  一行都不会建，库里只剩 `collection_key = "111"` 这种媒体 id，
  他根本认不出那是「学习」还是「音乐」。
  改成**按收藏夹分批**：一组一批，各带自己的 key、名字和终批。
  取数器本来就把名字带回来了（`cursor.collections`），只是没人转发。
- **而这个改动当场引出一条会删数据的路，被判据抓住了。**
  `apply_complete_scan`（消失检测）有两个调用点：收藏夹级终批一个、
  关系级终批一个。按收藏夹分批之后两个都会跑，**一次同步给同一条关系记两次缺席**
  ——而"连续两次缺席才关闭"这个设计的全部意义，就是让**一次**读漏
  （网络抖动、翻页卡住）不至于销账。两次并作一次，那道保险等于没有：
  取消收藏后**一次同步就销账**，一次失败的读也一样。
  修法在服务端：同一次同步里，一个收藏夹只许记一次缺席。
  这条此前是死的（DOM 抓取器删掉后没人发收藏夹级终批），所以一直没暴露。

## v0.0.0.8 — 多平台聚合真的发生了

Owner 2026-08-06 的验收原话：「我希望最后我来验收能给到我的是一个**操作简单、
满足要求、多平台聚合到一起的**一个软件。不要永远把任何的半成品推到我面前来。」

在这一版之前，能自动同步的只有 **Chrome 书签**一个——九个平台里八个
`sync_supported=false`。「多平台聚合」那句话没有兑现。

### B 站收藏夹能自动读了（G1 / G3）

- 取数缝隙 `acquireRelationItems()` 自 T03 删掉 DOM 抓取器后一直是显式 stub。
  原计划（T08/T10）是在浏览器里拦平台响应，但那条路要 Owner 先去收藏夹页
  按一次诊断把接口地址抓出来——**那正是他说的「不要让我和你重复地反攻」**。
  改成主动调 B 站自己的公开 REST 接口，请求从他自己的 B 站页面里发出去：
  零费用、不用他粘任何东西、不用他按任何诊断按钮，
  **Cookie 不出浏览器**（带凭据的是浏览器本身，这段代码从不读/存/传 cookie）。
- 翻页终点由接口自己的 `has_more` 决定，再和 `info.media_count` 对账——
  到没到底不用猜。对不上就报 partial，不报 complete
  （报了 complete 会让"消失检测"把没读到的当成他取消了收藏，那是会丢数据的）。
- 实测：公开收藏夹声明 10 条 / 读到 10 条 / 翻 3 页 / 跳过 0 条。
- 两个用测量换来的判断：**`code:0` 不等于读到了**（看不见的收藏夹回

- 真 Chrome 端到端演练（`scripts/bilibili_end_to_end_drill.py`）：

# 2026-09-06：固定端口守卫把 lsof 的失败当成了端口故障

## 现象

启动 Kimi Code Desktop 弹两种框，交替出现：

- `无法使用固定后台端口 58627：无法确认端口进程身份：Command failed: /usr/sbin/lsof -nP -t -iTCP:58627 -sTCP:LISTEN。请先正常退出已有 Kimi Code。`
- `Command failed: /usr/sbin/lsof -nP -t -iTCP:58627 -sTCP:LISTEN`（裸的，没有外壳）

## 根因

`server.cjs` 用 `lsof` 判定谁在占端口，而 `execFileText` 的超时写死 3000ms。

本机挂着 `//192.168.0.1/share`（smbfs）。同一条 lsof 查询连跑 5 次实测：

```
0.51s  3.53s  0.94s  0.27s  0.38s
```

**五次里有一次超过 3 秒。** 超时后 `execFile` 杀掉 lsof 并抛 `Command failed: <cmd>`，
而两个调用点都把这个异常当成「端口有问题」：

| 调用点 | 旧行为 |
|---|---|
| `inspectExistingServer` | `catch` 成 `occupied` → `startKimiServer` 拒绝启动 |
| `startLaunchdServer` | 完全没有 catch，异常直接穿到弹框 |

第二处还漏掉了清理：异常绕过了 `removeLaunchdJob`，**刚提交的 launchd 后台服务被留在那里继续监听**。
于是下次启动看到端口被占，走进第一处，弹另一种框 —— 两种弹框就是这么交替的。

还有一个独立缺陷：`lsof` 查无匹配时退出码就是 1、stderr 为空。
那是「没有人占用」，旧代码同样按异常处理，**空端口也会被判成故障**。

## 改法

1. **进程身份改问 launchd。** 后台服务是我们自己用固定 label 提交的，`launchctl list <label>` 直接给 PID，
   不扫全机文件表，也就不受网络卷拖慢影响。lsof 降级为交叉校验：查得出就必须对得上，查不出不构成失败。
2. **lsof 调用加 `-b -w`、超时提到 10s。** `-b` 跳过会阻塞的内核调用（实测 `-i` 查询与 txt 路径解析都不受影响）。
3. **区分「查无匹配」和「查询失败」。** 退出码 1 且 stderr 为空 → 返回空结果，不是异常。
4. **认不出占用者不再拒绝启动。** 只有「另一个 Kimi Code GUI 正在管这个后台」算真冲突；
   其余（被别的程序占、查不出身份）一律换临时端口照常开 —— 固定端口只是偏好，
   App 全程读 `runtime.port`，没有任何地方读常量。
5. **`startLaunchdServer` 整段包 try/catch**，任何失败路径都收走 launchd 任务，不再漏后台。

## 验收（本机实测三种场景）

| 场景 | 结果 |
|---|---|
| 干净启动 | 后台起在 58627，HTTP 200 |
| GUI 崩溃、后台遗留后重启 | 接管同一个 PID，不重开后台，无弹框 |
| 58627 被无关程序占住 | 降级到临时端口 52122，App 正常打开 |

回归测试 4 条写进 `test/server.test.cjs`；其中「空端口不得暴露 lsof 原始报错」一条
在旧代码上确认为红。全套 37 项通过。

## 教训

**外部命令的非零退出码不等于「被查的东西有问题」。**
`lsof` 超时是本机环境问题，`lsof` 退出码 1 是「没找到」，两者都被当成了「端口不可用」。
判定别人的状态之前，先分清「我没查到」和「它有问题」。

**能问权威来源就别去推断。** 后台服务是自己提交给 launchd 的，PID 本来就有账可查，
却绕道去扫全机 socket 表 —— 又慢又脆。
